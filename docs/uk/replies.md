# Сценарії відповідей

Відправник має витримувати отримувачів, які відповідають повільно,
зависають, падають або час від часу помиляються. Сторінка **Behaviour**
кожного ендпоінта задає, як він відповідає, тож можна навмисно відтворити
саме це і подивитися, що робитиме відправник.

Відкрийте її кнопкою **Behaviour** на сторінці Endpoints або на реєстрі. На
ній вкладки за частинами: **Checks**, **Rules**, **Default**, **Variables**,
**Secrets**, **Schemas**. Зміни діють з наступного запиту.

![Вкладка Rules ендпоінта /billing/notify: перші 2 запити отримують 503, далі кожен 3-й — 500](../images/behaviour-rules.webp)

## Як обирається відповідь

1. Спершу працюють **перевірки**. Обов'язковий заголовок, примусова
   [перевірка автентичності](authorization.md) або примусова
   [перевірка схеми](schemas.md) можуть відмовити запиту (`400` чи `401` або
   ваша власна відповідь). Запит, якому відмовили, не враховується правилами.
2. Далі **правила**, по черзі. Вирішує перше правило, чия умова виконується;
   решта пропускаються.
3. Решті запитів відповідає **типова відповідь**. Спершу це `200` з порожнім
   тілом.

Кожен запит записує, що з ним зробили: правило чи типова відповідь, статус
і надіслані заголовки, виміряна затримка або скільки відправник чекав на
таймауті.

## Правила

На вкладці **Rules** натисніть **New rule** і виберіть:

- **When**: `every Nth request` (кожен N-й), `the first N requests` (перші N
  від скидання лічильника) або `at random, p%` (випадково, з імовірністю).
- **Do**: `reply as below` (статус, заголовки, тіло, затримка з випадковим
  розкидом), `time out: hold, never answer` (тримати і не відповідати) або
  `drop: reset the connection` (обірвати з'єднання).

![Діалог Rule 1: перші 2 запити, відповідь 503 із Retry-After: 2](../images/behaviour-rule-edit.webp)

Стрілки пересувають правило вгору чи вниз; порядок має значення. Лічильник
на вкладці Rules рахує запити, які бачили правила; **Reset counter**
запускає його знову, тож «перші 2 запити» можна відтворити ще раз.

### Провалювати кожну третю доставку

Правило: кожен 3-й запит, відповідь `500`.

<!-- docs-check: setup: every_third -->
```sh
H=http://127.0.0.1:8080/billing/notify
curl -s -d '{"invoice":"in_1"}' $H   # 200
curl -s -d '{"invoice":"in_2"}' $H   # 200
curl -s -d '{"invoice":"in_3"}' $H   # 500 from rule 1
```

### Провалити перші дві, потім відновитися

Правило: перші 2 запити, відповідь `503` із заголовком `Retry-After: 2`.
Відправник із повторами й backoff має доставити з третьої спроби; сторінка
запиту покаже `delivery 3 of this body`, а звіт — проміжки між доставками.
Натисніть **Reset counter**, щоб прогнати знову.

<!-- docs-check: setup: first_two -->
```sh
H=http://127.0.0.1:8080/billing/retry
curl -s -d '{"invoice":"in_7"}' $H   # 503
curl -s -d '{"invoice":"in_7"}' $H   # 503
curl -s -d '{"invoice":"in_7"}' $H   # 200
```

### Повільний отримувач

Типова відповідь: затримка `2000` мс (додайте розкид, щоб час різнився).
Затримка вимірюється і записується разом із запитом.

<!-- docs-check: setup: slow -->
```sh
curl -s -o /dev/null -w '%{http_code} after %{time_total} s\n' -d '{}' http://127.0.0.1:8080/billing/slow
# 200 after 2.…
```

Якщо відправник здався раніше, ніж минула затримка, він відповіді не
отримав: запит записано як **sender left**, а стрічка і звіти рахують його
як таймаут, не як успіх.

### Отримувач, що зависає

Правило: time out (з `at random, 10%` зависатиме лише частина запитів).
Hookwitness тримає з'єднання і не відповідає, доки відправник не здасться
або не мине `-max-wait` (типово 5 хвилин); тоді закриває з'єднання без
відповіді. Сторінка запиту показує, скільки чекав відправник.

<!-- docs-check: setup: hang -->
```sh
curl -s -m 2 -o /dev/null -w '%{http_code}\n' -d '{}' http://127.0.0.1:8080/billing/hang
# 000
```

### Отримувач, що падає

Правило: drop. З'єднання скидається (TCP RST), щойно запит прочитано, як це
зробив би отримувач, що впав; запит усе одно зберігається.

<!-- docs-check: setup: crash -->
```sh
curl -s -o /dev/null -w '%{http_code}\n' -d '{}' http://127.0.0.1:8080/billing/crash
# 000
```

## Типова відповідь

Вкладка **Default** задає відповідь запитам, яким не відмовила жодна
перевірка і не підійшло жодне правило: статус, заголовки, тіло, затримку і
розкид.

![Вкладка Default ендпоінта /slack/events: 200 і challenge у JSON-тілі](../images/behaviour-default.webp)

### Повернути challenge для перевірки адреси

Деякі відправники перевіряють URL, перш ніж ним користуватися (Slack
надсилає `challenge` і чекає його назад). Типова відповідь: заголовок
`Content-Type: application/json`, тіло `{"challenge":"{{.JSON "challenge"}}"}`.

<!-- docs-check: setup: challenge -->
```sh
curl -s -d '{"type":"url_verification","challenge":"3eZb"}' http://127.0.0.1:8080/slack/events
# {"challenge":"3eZb"}
```

## Шаблони

Значення заголовків і тіла відповідей — шаблони Go над запитом:

| Шаблон | Дає |
|---|---|
| `{{.Header "X-Request-Id"}}` | заголовок запиту (перший із цим іменем) |
| `{{.Query "name"}}` | параметр query |
| `{{.JSON "event.items.0.id"}}` | поле JSON-тіла за шляхом через крапку |
| `{{.Var.TOKEN}}` | змінну з вкладки **Variables** |
| `{{.N}}` | номер запиту від скидання лічильника |
| `{{.Method}}`, `{{.Path}}`, `{{.Body}}` | сам запит |

Працюють `if`, `with` і стандартні функції; `range` і вкладені шаблони — ні.
Рендер обмежено 1 MiB і однією секундою. Шаблон, що не спрацював, дає
відповідь `500` і назву помилки на сторінці запиту.

**Змінні** (`NAME=value`) — тестові значення для шаблонів. Їх видно
відкритим текстом, тож ніколи не кладіть туди справжніх секретів; для
секретів є окрема вкладка ([Перевірки автентичності й секрети](authorization.md)).

Заголовки відповіді йдуть так, як їх пише HTTP-сервер Go: відсортовані за
іменем, повторений заголовок зберігає свій порядок. `Content-Length`,
`Transfer-Encoding` і `Connection` належать серверу, задати їх не можна.

## Обов'язкові заголовки

Перевірка **Required header** на вкладці **Checks** відмовляє запиту без
заголовка або з заголовком, що не дорівнює значенню чи не відповідає
регулярному виразу. Відмова — `400` із назвою заголовка або ваша власна
відповідь.

Вимагайте API-ключ, як справжній клієнт: заголовок `X-Api-Key` має
дорівнювати `key_test`, власна відповідь — `401` з JSON-тілом.

<!-- docs-check: setup: api_key -->
```sh
H=http://127.0.0.1:8080/partner/hooks
curl -s -d '{}' -H 'X-Api-Key: key_test' $H   # 200
curl -s -d '{}' -H 'X-Api-Key: nope' $H       # 401 refused by the check
```
