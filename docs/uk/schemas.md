# Перевірки JSON Schema

Чи тримає подія свій контракт? Перевірка JSON Schema валідує тіло кожного
запиту і записує вердикт поруч із вердиктами автентичності:

- **pass** — пройшов;
- **fail** — до 20 проблем, кожна з JSON pointer у тілі, ключовим словом, що
  не пройшло, і повідомленням;
- **n/v** — тіло не збережене (більше за ліміт);
- **n/c** — не перевірено: до події не застосовується жодна схема.

## Додати схему й перевірку, крок за кроком

Приклад на цій сторінці — ендпоінт `/orders/events`, чиї події несуть свій
вид у `/type`. Події виду `order.paid` мають відповідати схемі `OrderPaid`:

```json
{"type":"object","required":["order_id","amount"],
 "properties":{"order_id":{"type":"integer"},"amount":{"type":"integer","minimum":1},
               "paid_at":{"type":"string","format":"date-time"}}}
```

1. Відкрийте сторінку **Behaviour** ендпоінта `/orders/events`, вкладку
   **Schemas**, і натисніть **New schema**. Назвіть її `OrderPaid` і вставте
   схему або завантажте файл. Hookwitness не збереже неправильну схему і
   пояснить чому.
2. Відкрийте вкладку **Checks**, натисніть **New check** і виберіть тип
   **JSON Schema**. У **Pick the schema by** виберіть **a value in the body
   (JSON pointer)**, введіть `/type` і задайте зіставлення
   `order.paid = OrderPaid`. Збережіть.

Ендпоінт на знімках має ще одну схему, `ReceiptScanned`, для
[зображень](#зображення-в-даних) нижче.

![Вкладка Schemas ендпоінта /orders/events з OrderPaid і ReceiptScanned](../images/schemas.webp)

![Діалог перевірки, що вибирає схему за /type](../images/schema-check.webp)

Тепер надішліть три події: одну, що відповідає схемі, одну, що не
відповідає, і одну такого виду, для якого схеми немає.

<!-- docs-check: setup: orders -->
```sh
H=http://127.0.0.1:8080/orders/events
curl -s -d '{"type":"order.paid","order_id":42,"amount":1999,"paid_at":"2026-10-12T17:28:07Z"}' $H   # pass
curl -s -d '{"type":"order.paid","order_id":"42","paid_at":"yesterday"}' $H                        # fail: 3 errors against OrderPaid
curl -s -d '{"type":"order.created","order_id":43}' $H                                              # n/c: no schema for /type "order.created"
```

Сторінка другого запиту ставить штамп із вердиктом
(`Schema: fail, 3 errors`), перелічує проблеми і позначає місця в тілі, де
вони є:

![Сторінка другого запиту з трьома проблемами](../images/schema-fail.webp)

## Що вміють схеми

- **Версію стандарту** визначає `$schema`: від draft-04 до 2020-12, а без
  нього — 2020-12.
- **`format` перевіряється.** `date-time` зі значенням `"yesterday"` не
  пройде.
- **Посилання за іменем.** Схеми одного ендпоінта посилаються одна на одну
  через `{"$ref": "Address"}`. Нічого ніколи не завантажується, тож
  посилання на будь-який інший URL чи файл відхиляється під час збереження.
- **Тіло, що не є JSON**, не проходить, з помилкою розбору і позицією в
  байтах. Порожнє тіло не проходить як порожнє.

## Яка схема застосовується

Перевірка використовує одне з трьох.

- **Одну схему.** Кожне тіло має їй відповідати.
- **Кілька**, коли відправник може надсилати будь-яку з форм (v1 чи v2).
  Тіло має відповідати одній із них, і вердикт називає яку. Коли не підходить
  жодна, вердикт дає проблеми найближчої і наскільки далекі інші, наприклад
  `matches none of V1, V2; closest V2 with 1 error (V1: another shape)`.
- **Схему, вибрану за значенням**, як у прикладі: JSON pointer у тілі
  (`/type`) або заголовок (`X-GitHub-Event`), зі зіставленням по одному на
  рядок, наприклад `order.paid = OrderPaid`. Значення без зіставлення або
  запит без значення перевіряються за типовими схемами, якщо вони є. Без
  типової запит отримує **n/c**, і йому ніколи не відмовляють.

## Enforce

З **Enforce** тілу, що не пройшло, відмовляють ще до правил, тож його не
враховано. Відмова — `400` з переліком проблем або ваша власна відповідь.
Тілу, яке не вдалося перевірити (n/v), теж відмовляють; n/c — ніколи.

## Чернетка схеми з упійманого

Найдовше — писати схему для кожного типу подій вручну. Нехай чернетку
складуть упіймані тіла:

1. Натисніть **Draft schema** на запиті або на реєстрі для кількох запитів.
   На реєстрі їх вибирають за номерами (`3, 5-9`) або беруть усі запити з
   тим самим значенням дискримінатора перевірки (`/type = order.shipped`).

   ![Діалог Draft schema з усіма запитами, де /type — order.shipped](../images/draft-dialog.webp)

2. Редактор схеми відкривається з чернеткою. У ній побачені типи, ключі
   (обов'язкові, коли вони є в кожному тілі), елементи масивів і формати
   рядків (`date-time`, `date`, `uuid`, `email`, `uri`), коли їх мають усі
   значення. Ім'я пропонується зі значення: `order.shipped` стає
   `OrderShipped`.

   ![Редактор схеми з чернеткою OrderShipped](../images/draft-editor.webp)

3. Перегляньте її, бо чернетка знає лише те, що було в цих тілах. Переліки,
   шаблони, діапазони й довжини ніколи не вгадуються. Нічого не зберігається,
   доки ви не натиснете **Save schema**.

Якщо є перевірка з дискримінатором, редактор пропонує зіставити значення з
новою схемою в цій перевірці. Якщо схема з таким іменем уже є, редактор
показує, що змінить чернетка (додані ключі, ключі, що стали
необов'язковими, ширші типи), і збереження її замінює. Запити, упіймані
раніше, лишаються **n/c**, доки ви не перевірите їх знову (див.
[Вердикти й повторна перевірка](endpoints.md#вердикти-й-повторна-перевірка)).

## Зображення в даних

Рядок, оголошений зображенням, має справді ним бути:

```json
{"type":"string","contentEncoding":"base64","contentMediaType":"image/png"}
```

Так само працюють `image/jpeg`, `image/gif` і `image/webp`, а `image/*`
приймає будь-який із них. Приймається й URL `data:image/...;base64,`.
Зображення декодується повністю, тож обрізана картинка, картинка іншого типу,
ніж оголошено, текст або SVG не проходять на своєму шляху. Зображення можуть
мати до 40 мегапікселів. HEIC і AVIF розпізнаються, але декодувати їх тут не
можна, тож їхній вердикт — n/v.

Декодування обмежене пам'яттю, а не лише пікселями: зображення, якому для
декодування потрібно понад 128 MB (16-бітному PNG 4000×4000 потрібно), або
зображення після перших 256 MB одного запиту перевіряються лише за заголовком
і позначаються *not checked*; тоді вердикт — n/v із причиною. Кожне
зображення декодується один раз за перевірку, а повторний показ запиту не
декодує його знову.

Сторінка запиту показує зображення над тілом: оголошені схемою, звичайні
рядки `data:image` і тіло, яке саме є зображенням. Кожне можна переглянути в
повний розмір і завантажити. Звіти теж їх містять. На знімку поле `scan`
квитанції оголошене як PNG у схемі `ReceiptScanned`:

![Запит зі сканом квитанції над тілом](../images/payload-images.webp)

## Після зміни схеми

**Re-check** знову валідує всі збережені запити з поточними схемами; див.
[Вердикти й повторна перевірка](endpoints.md#вердикти-й-повторна-перевірка).

## Через API

Схеми й перевірки схем — частина документа поведінки. `POST
/endpoints/{id}/schema-draft` складає чернетку, нічого не зберігаючи. Див.
[довідник API](../api.md#behaviour).
