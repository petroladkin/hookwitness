# Перевірки JSON Schema

Чи тримає подія свій контракт? Перевірка JSON Schema валідує тіло кожного
запиту і записує вердикт поруч із вердиктами автентичності:

- **pass** — пройшов;
- **fail** — до 20 проблем, кожна з JSON pointer у тілі, ключовим словом, що
  не пройшло, і повідомленням;
- **n/v** — тіло не збережене (більше за ліміт);
- **n/c** — не перевірено: до події не застосовується жодна схема.

## Додати схему й перевірку, крок за кроком

1. Відкрийте сторінку **Behaviour** ендпоінта, вкладку **Schemas**, і
   натисніть **New schema**. Назвіть її (`OrderPaid`) і вставте схему або
   завантажте файл. Неправильну схему не збереже — з поясненням чому.
2. Відкрийте вкладку **Checks**, натисніть **New check** і виберіть тип
   **JSON Schema**. Виберіть схему і збережіть.

![Вкладка Schemas ендпоінта /orders/events: OrderPaid і ReceiptScanned](../images/schemas.webp)

Схема з прикладу нижче:

```json
{"type":"object","required":["order_id","amount"],
 "properties":{"order_id":{"type":"integer"},"amount":{"type":"integer","minimum":1},
               "paid_at":{"type":"string","format":"date-time"}}}
```

Сторінка запиту ставить штамп із вердиктом (`Schema: fail, 3 errors`),
перелічує проблеми і позначає місця в тілі, де вони є.

![Запит, що не пройшов схему: проблемні ключі позначено в тілі, три проблеми в списку](../images/schema-fail.webp)

## Що вміють схеми

- **Чернетки стандарту** визначає `$schema`: від draft-04 до 2020-12, а без
  нього — 2020-12.
- **`format` перевіряється**: `date-time` зі значенням `"yesterday"` не
  пройде.
- **Посилання за іменем**: схеми одного ендпоінта посилаються одна на одну
  через `{"$ref": "Address"}`. Нічого ніколи не завантажується: посилання на
  будь-який інший URL чи файл відхиляється під час збереження.
- **Тіло, що не є JSON**, провалюється з помилкою розбору і позицією в
  байтах; порожнє тіло провалюється як порожнє.

## Яка схема застосовується

Перевірка використовує:

- **одну схему**: кожне тіло має їй відповідати;
- **кілька**, коли відправник може слати будь-яку з форм (v1 чи v2): тіло
  має відповідати одній із них, і вердикт називає яку. Коли не підходить
  жодна, він дає проблеми найближчої і наскільки далекі інші:
  `matches none of V1, V2; closest V2 with 1 error (V1: another shape)`;
- **схему, вибрану за значенням**: JSON pointer у тілі (`/type`) або
  заголовок (`X-GitHub-Event`), з відповідністю `order.paid = OrderPaid`,
  по одній на рядок. Значення без відповідності або запит без значення
  перевіряються за типовими схемами, якщо вони є; без типової запит
  отримує **n/c** і йому ніколи не відмовляють.

![Діалог перевірки: JSON Schema за /type, зіставлено два значення](../images/schema-check.webp)

Ендпоінт `/orders/events` зі схемою `OrderPaid` вище і перевіркою, що
вибирає її за `/type` із відповідністю `order.paid = OrderPaid`:

<!-- docs-check: setup: orders -->
```sh
H=http://127.0.0.1:8080/orders/events
curl -s -d '{"type":"order.paid","order_id":42,"amount":1999,"paid_at":"2026-10-12T17:28:07Z"}' $H   # pass
curl -s -d '{"type":"order.paid","order_id":"42","paid_at":"yesterday"}' $H                        # fail: 3 errors against OrderPaid
curl -s -d '{"type":"order.created","order_id":43}' $H                                              # n/c: no schema for
```

## Enforce

З **Enforce** тілу, що не пройшло, відмовляють із `400` і переліком проблем
(або вашою відповіддю) ще до правил, тож його не враховано. Тілу, яке не
вдалося перевірити (n/v), теж відмовляють; n/c — ніколи.

## Чернетка схеми з упійманого

Найдовше — писати схему для кожного типу подій вручну. Нехай чернетку
складуть упіймані тіла:

1. Натисніть **Draft schema** на запиті або на реєстрі для кількох:
   вибраних за номерами (`3, 5-9`) або всіх запитів з тим самим значенням
   дискримінатора перевірки (`/type = order.shipped`).

   ![Діалог Draft schema: усі запити з /type order.shipped](../images/draft-dialog.webp)

2. Редактор схеми відкривається з чернеткою: побачені типи, ключі
   (обов'язкові, коли вони є в кожному тілі), елементи масивів і формати
   рядків (`date-time`, `date`, `uuid`, `email`, `uri`), коли їх мають усі
   значення. Ім'я пропонується зі значення (`order.shipped` → `OrderShipped`).

   ![Редактор схеми з чернеткою і пропозицією зіставити order.shipped із нею](../images/draft-editor.webp)

3. Перегляньте її: чернетка знає лише те, що було в цих тілах. Переліки,
   шаблони, діапазони й довжини ніколи не вгадуються. Нічого не зберігається,
   доки ви не натиснете **Save schema**.

Якщо є перевірка з дискримінатором, редактор пропонує зіставити значення з
новою схемою в цій перевірці. Якщо схема з таким іменем уже є, він показує,
що змінить чернетка (додані ключі, ключі, що стали необов'язковими, ширші
типи), і збереження її замінює. Запити, упіймані раніше, лишаються **n/c**,
доки ви не натиснете **Re-check**.

## Зображення в даних

Рядок, оголошений зображенням, має справді ним бути:

```json
{"type":"string","contentEncoding":"base64","contentMediaType":"image/png"}
```

Так само працюють `image/jpeg`, `image/gif`, `image/webp` або `image/*` для
будь-якого з них, і приймається URL `data:image/...;base64,`. Зображення
декодується повністю, тож обрізана чи неправильно підписана картинка, текст
або SVG провалюються на своєму шляху. До 40 мегапікселів. HEIC і AVIF
розпізнаються, але декодувати їх тут не можна, тож їхній вердикт — n/v.

Сторінка запиту показує зображення під тілом: оголошені схемою, звичайні
рядки `data:image` і тіло, яке саме є зображенням, з переглядом у повний
розмір і завантаженням. Звіти теж їх містять.

![Запит із зображенням, оголошеним схемою: мініатюра над тілом, base64 у тілі скорочено](../images/payload-images.webp)

## Повторна перевірка

Після зміни схеми **Re-check** на реєстрі знову валідує всі збережені
запити. Змінюються лише вердикти.

## Через API

Схеми й перевірки схем — частина документа поведінки; `POST
/endpoints/{id}/schema-draft` складає чернетку, нічого не зберігаючи. Див.
[довідник API](../api.md#behaviour).
