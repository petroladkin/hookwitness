# Розв'язання проблем

Несподіванки, на які натрапляють найчастіше: що їх спричиняє і що робити.

## Секрет додано, але запити все одно отримують 200 і жодного вердикту

Сам секрет нічого не робить: це лише значення, яким користується перевірка.
Додайте перевірку: **Behaviour → Checks → New check**, потім виберіть тип
(Bearer token, Basic credentials, GitHub signature…) і секрет. Вкладка
Secrets показує перевірки, що користуються кожним секретом, а «not used: add
a check» означає, що жодна.

<!-- docs-check: setup: secret_only -->
```sh
curl -s -o /dev/null -d '{}' -H 'Authorization: Bearer wrong' http://127.0.0.1:8080/ping   # 200: no check, no verdict
```

Навіть з перевіркою запит, що її провалив, отримує звичайний `200`, якщо в
перевірки не ввімкнено **Enforce**: без нього перевірка лише записує
вердикт. Див. [Перевірки автентичності й секрети](authorization.md#enforce).

## Після повторного створення контейнера все зникло

Контейнер працював без тому для `/data`, тож база жила в самому контейнері
й зникла разом із ним. Відтепер запускайте його з іменованим томом
(`-v hookwitness:/data`); див.
[Налаштування й розгортання](deployment.md#тримайте-дані-в-томі). Те, що було
у видаленому контейнері, відновити не можна.

## Інтерфейс каже, що не відповідає на ім'я хоста

```text
The web UI does not answer to the host name "hooks.example.com:8080". Open it by IP address or localhost, or allow the name with -admin-hosts.
```

Інтерфейс і API відповідають лише на IP-адреси і `localhost`, щоб сторінка
з іншого домену не дістала їх, спрямувавши своє ім'я на ваш сервер (див.
[Доступ з інших машин](deployment.md#доступ-з-інших-машин)). Відкрийте за IP-адресою
або дозвольте ім'я: `-admin-hosts hooks.example.com` (у Docker:
`-e HOOKWITNESS_ADMIN_HOSTS=hooks.example.com`). API дає таку саму
відмову як `421 wrong_host`. Шляхи для вебхуків відповідають на будь-яке
ім'я.

```sh
curl -s -H 'Host: hooks.example.com' http://127.0.0.1:8080/admin/api/v1/endpoints | jq -r .error.code
# wrong_host
```

## Кожна перевірка підпису каже n/v: «cannot be decrypted (wrong secret key?)»

Сервер працює з іншим ключем секретів, ніж той, яким їх запечатано: змінено
`HOOKWITNESS_SECRET_KEY` або базу перенесли без її файлу `.key`. Під час
запуску лог про це каже:

```text
this secret key is not the one this database was used with: sealed signing keys cannot be opened and stored tokens never match
```

Запустіть його з початковим ключем (змінна або файл `.key` поруч із базою)
або задайте секрети знову кнопкою **Replace** на вкладці Secrets, а потім
знову перевірте збережені запити (див.
[Вердикти й повторна перевірка](endpoints.md#вердикти-й-повторна-перевірка)). Збережені токени й паролі
теж не відновити: з чужим ключем вони просто ніколи не збігаються.

## Запит отримав 413, а його перевірки кажуть n/v

Його тіло було більше за `-max-body` (типово 10 MiB). Він отримав `413` і
збережений без тіла, тож нічого, що потребує тіла (підпис чи схему),
перевірити не можна, і вердикт — **n/v**. Підніміть ліміт
(`HOOKWITNESS_MAX_BODY=50MiB`), якщо такі тіла очікувані.

З перевіркою GitHub зі сторінки
[Перевірки автентичності](authorization.md#приклад-для-кожної) на `/hooks`
тіло на 11 МБ отримує `413` і такий вердикт:

<!-- docs-check: setup: github -->
```sh
head -c 11000000 /dev/zero | curl -s -o /dev/null --data-binary @- http://127.0.0.1:8080/hooks   # n/v: body not kept (over the size limit)
```

## Запит отримав 503 «busy»

Hookwitness уже читав стільки байтів тіл запитів, скільки дозволяє
`-max-inflight` (за замовчуванням більше з 256 MiB і подвоєного
`-max-body`). Запит отримав `503` з `Retry-After: 5`, зберігся без тіла, а
реєстр пише **Busy**; відправник, який повторює спробу, проходить. Якщо так
буває за звичайного навантаження, збільште ліміт
(`HOOKWITNESS_MAX_INFLIGHT=1GiB`).

## Мої запити потрапляють в Unmatched із 404

Шлях не збігається з ендпоінтом точно. Порівняйте їх у реєстрі Unmatched:
скісна риска в кінці (`/hooks/` — це не `/hooks`), пропущений сегмент,
інший регістр. Виправте URL відправника або створіть ендпоінт із цим
шляхом.

## Відправник каже, що вийшов час, але в Hookwitness запит є

Затримка відповіді (або правило таймауту) була довшою за таймаут
відправника. Запит записано як **sender left**, із часом, скільки чекав відправник,
і пораховано як таймаут. Скоротіть затримку або лишіть, щоб перевірити саме
це.

## Перевірка Stripe чи Standard Webhooks провалюється з «timestamp … old»

Підписана позначка часу старша за допуск (300 с), зазвичай коли ви повторно
надсилаєте записаний запит. Поставте в перевірці **Accept any timestamp
(replayed captures)** або збільште її допуск.

## Реєстр не оновлюється сам

Живий реєстр — це потік Server-Sent Events на `/admin/e/<id>/events`.
Зворотний проксі, що буферизує відповіді, його затримує; вимкніть
буферизацію для префікса адмін-інтерфейсу (nginx: `proxy_buffering off;`; Hookwitness
також надсилає `X-Accel-Buffering: no`). Перезавантаження завжди показує
поточний стан.

## API відповідає 401, відколи додано користувача

Перший користувач вмикає вхід і для REST API та MCP: скриптам і агентам
тепер потрібен токен (`Authorization: Bearer <token>`, зі сторінки акаунта),
див. [Користувачі, вхід і токени](access.md#токени-для-скриптів-і-агентів).
`401 invalid_token` означає, що токен хибний чи відкликаний або його
власника видалено.

## Ніхто більше не може увійти

На сервері `hookwitness user passwd <name>` задає новий пароль, а
`hookwitness user add <name> --admin` додає ще одного адміністратора; див.
[Втрачено пароль адміністратора](access.md#втрачено-пароль-адміністратора).
Десять невдалих спроб з однієї адреси зупиняють її входи на 15 хвилин; за
зворотним проксі задайте `-trusted-proxies`, щоб пауза влучала в клієнта, а
не в проксі.
